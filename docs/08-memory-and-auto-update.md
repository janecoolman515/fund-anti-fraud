# 记忆功能与自动更新 · 设计方案

> **状态：设计完成，后端待接入。**
>
> 本文描述的是"用户提交的资料如何累积、合并、自动补全"的完整方案。
> 当前线上版本是纯静态页，只有单次分析；记忆与自动更新需要云服务（数据库 + LLM）才能落地。

---

## 一 · 为什么必须做记忆

单次分析的致命缺陷：**资料不全 → 分数偏低 → 用户以为安全**。

一个真实场景：

| 谁 | 提交了什么 | 单次分析结果 |
|---|---|---|
| 张三 | "日化 1.2%，推荐三人返佣" | 识别 2 项 → 🟡 中风险 |
| 李四 | "要买 998 套餐才能激活，本金锁 30 天" | 识别 2 项 → 🟡 中风险 |
| **合并后** | 日化 1.2% + 拉人计酬 + 门槛费 + 锁仓 | **🔴 82 分 极高风险** |

**信息在两个人手里，各看一半都是中风险，合起来才是完整画像。**

这就是记忆功能的价值：**让分散的信息沉淀成完整档案。**

## 二 · 数据模型

三张表，职责分离：

### 1. `projects` —— 项目档案（合并后的结果）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 主键 |
| `name` | string | 项目名（归一化后） |
| `aliases` | array | 别名 / 曾用名（换皮盘的关键线索） |
| `facts` | object | **合并后的结构化事实**（21 个字段） |
| `score` | int | 合并后的风险分 |
| `level` | string | 评级 |
| `coverage` | float | 信息完整度 |
| `submission_count` | int | 被提交过多少次 |
| `contributor_count` | int | 多少个不同来源 |
| `first_seen` / `last_update` | timestamp | 时间线 |
| `needs_review` | bool | 是否需要人工复核 |

### 2. `submissions` —— 每次提交的原始记录（不合并）

| 字段 | 说明 |
|---|---|
| `project_id` | 外键 |
| `raw` | 用户提交的原文（项目名、制度、话术、网站） |
| `parsed` | 解析出的字段（含每项的依据原文） |
| `stage` | 用户当时的状态 |
| `source` | 来源渠道（网页 / 小程序 / 微信） |
| `created_at` | 时间 |

**为什么保留原始记录**：合并会丢信息。原始记录是回溯和纠错的唯一依据。

### 3. `fact_evidence` —— 每个字段的证据链

| 字段 | 说明 |
|---|---|
| `project_id` | 外键 |
| `field` | 字段名（如 `daily_rate`） |
| `value` | 值 |
| `evidence` | 原文依据（"日化1.8%"） |
| `submission_id` | 来自哪次提交 |

**这一张表是整个系统可信度的基础**：报告里每个数字都能追到"是谁在哪次提交里说的什么原话"。

## 三 · 合并规则

**核心原则：新信息补充空缺，冲突取更保守值。**

### 3.1 字段合并

```python
def merge(old, new):
    if old is None:              return new        # 空缺 → 补上
    if new is None:              return old
    if old == new:               return old
    # 冲突：取「更危险」的那个
    return more_conservative(old, new, field)
```

### 3.2 「更保守」怎么定义

不同字段的保守方向不同：

| 字段类型 | 保守方向 | 例子 |
|---|---|---|
| 收益率 | **取更高** | 1.2% vs 1.8% → 取 1.8% |
| 分销层级 | **取更多** | 2 级 vs 3 级 → 取 3 |
| 门槛费 | **取更高** | 399 vs 998 → 取 998 |
| 布尔型（锁仓/保本/提现受限） | **任一为真即真** | 一人说有 → 取"有" |
| 备案主体 | **取更弱** | 企业 vs 个人 → 取个人 |
| 造血业务 | **取更差** | real vs weak → 取 weak |

### 3.3 冲突要留痕

**冲突本身就是强信号。** 两个来源说法不一致，说明：
- 项目方在不同渠道用不同话术
- 或者其中一方记错 / 被误导

所以 `projects` 要记录 `conflicts` 数组：

```json
"conflicts": [
  { "field": "daily_rate", "values": [1.2, 1.8],
    "note": "两个来源说法不一致，取高值 1.8%" }
]
```

报告里要显示："关于收益率，有两个来源分别说是 1.2% 和 1.8%，本报告按 1.8% 计。"

## 四 · 自动更新流程

### 4.1 用户提交时（实时）

```
用户提交
  → 解析（正则 + 关键词，前端已实现）
  → 按项目名归一化匹配已有档案
      ├─ 命中 → 合并 facts → 重算分 → 更新 projects
      └─ 未命中 → 新建 projects 记录
  → 写入 submissions + fact_evidence
  → 返回「合并后的评分」+「本次新增了什么」
```

**关键交互**：不只显示"这次多少分"，还要显示**"你的提交让这个项目的分数从 X 变成了 Y"**。
这会让用户感到自己的贡献是有价值的。

### 4.2 用户退出后（异步）

```
定时任务 / 提交触发
  → 取出 needs_review = true 的项目
  → 调 LLM 做三件事：
      ① 从原始文本里二次抽取（补正则漏掉的）
      ② 生成「待核查清单」：还缺什么、去哪查
      ③ 判断项目类型（资金盘/数藏/抢矿/抢单…）
  → 更新 facts + 生成 review_notes
```

### 4.3 关于「自动上网搜集」

**必须说清的限制**：

免密钥 LLM 调用**不保证带实时联网**。如果它没有联网能力，
所谓"自动搜集互联网资料"就会变成"用模型内部知识编"，这比不搜集更危险。

**因此分两步走**：

| 阶段 | 做法 | 可靠性 |
|---|---|---|
| **第一步（现在能做）** | LLM 只做**整理**：把用户提供的零散文本结构化、找矛盾、列缺口。**不生成任何用户没说过的事实。** | 高 |
| **第二步（需另接搜索）** | 接搜索 API（如必应/谷歌/百度），按项目名 + 关键词检索备案、工商、投诉、判决，把结果存进 `fact_evidence` 并标注来源 | 取决于搜索源 |

**第一阶段的硬规则**：

> **LLM 不允许新增"用户没提供、也没有公开来源"的事实。**
> 它只能：整理、去重、找矛盾、列缺口、判断类型。
>
> 这条规则写进 prompt，也写进代码校验：LLM 输出的每个字段必须带 `evidence`，
> 没有 evidence 的字段直接丢弃。

## 五 · 评分要跟着变

合并后重算分，但**要区分两种分数**：

| 分数 | 含义 | 展示 |
|---|---|---|
| **本次评分** | 只看你这次提交的资料 | 主分数，旁边跟免责提示 |
| **累计评分** | 合并所有来源后的档案评分 | 副分数，标注"N 人提交" |

**为什么两个都显示**：
- 只显示累计分，用户会觉得"跟我没关系"
- 只显示本次分，用户会低估风险

### 免责提示（已上线）

放在评分正下方，金色边框，不可折叠：

> **这个分数只代表你提交的这些资料**
> 你填得越少，分数越**不准** —— 不是偏高，是**偏低**。
> 没提供的项系统不会扣分，**不代表它没问题**。

## 六 · 隐私与合规

| 问题 | 处理 |
|---|---|
| 提交者身份 | **不收集**。不做登录，不存 IP，不存设备指纹 |
| 原始文本里的个人信息 | 入库前正则脱敏（手机号、身份证、银行卡、微信号） |
| 项目方能不能查到是谁提交的 | 不能。没有身份字段，只有时间戳 |
| 数据会不会被拿去卖 | 不会。只用于风险分析，公开页面只展示合并后的事实 |
| 用户能不能要求删除 | 能。提供 `delete by submission_id`，同时重算项目分 |

**一条额外的纪律**：

> 合并后的档案**不公开项目全名**，只公开"结构特征"和评分。
> 公开点名会带来法律风险，也会让项目方提前换皮。

## 八 · 接入时要改的地方

云服务开通后，按这个顺序改：

1. **`site/index.html`** 顶部引入云 SDK（CDN 形式，单文件项目）
2. **`renderParse()`** 里，提交后调 `cloud.database` 写入 `submissions`
3. **新增 `lookupProject(name)`**：查 `projects` 表，命中则显示累计评分
4. **新增 `mergeAndScore(projectId)`**：合并 facts → 重算 → 写回
5. **新增后台任务**：`needs_review = true` 的项目 → 调 `cloud.llm` 做整理
6. **发布**：用 `workbuddy_sites_deploy`，复用同一个 `applicationId`（否则云服务 Origin 校验会失败）
